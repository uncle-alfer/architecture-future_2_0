# Технологический радар Future 2.0

Этот документ опирается на:
- целевую архитектуру контейнеров из Task1 (`future2.0-containers.drawio.xml`);
- домены и потоки данных из Task2 (`domains-and-data-flows.md`);
- перечень проблем P1–P8 и бизнес-сценариев S1–S5 из `problems-and-prioritization.md`.

Обозначения бизнес-сценариев те же:

- **S1 - быстрая подготовка отчётности**;
- **S2 - независимое развитие финтех-направления**;
- **S3 - независимое развитие ИИ-направления**;
- **S4 - масштабирование для новых бизнесов и партнёров**;
- **S5 - безопасность и соответствие регуляторным требованиям**.


## 1. Структура техрадара

### 1.1. Квадранты

Для Future 2.0 используются четыре квадранта:

1. **Языки и фреймворки** - основа прикладной и data-разработки (Python, SQL, Go/Java, PowerBuilder и др.).
2. **Инструменты** - BI/портал самообслуживания, каталог данных, средства CDC/ETL, мониторинг, DataAPI и др.
3. **Платформы и операции** - облако, Data Lakehouse, стриминговая платформа, Legacy DWH, ESB, операционные ядра доменов.
4. **Практики и паттерны** - Data Mesh, доменные data products, федеративное управление данными, DataOps/MLOps, IaC и др.


### 1.2. Кольца

Кольца описывают зрелость и целевой статус технологий в ландшафте Future 2.0:

- **Adopt («используем»)** - устоявшиеся технологии, применяются в проде и рекомендуются к применению в новых инициативах.
- **Trial («пробуем»)** - активно пилотируемые технологии: уже есть пилоты/МVP, но ограниченный масштаб и не везде есть экспертиза.
- **Asset («изучаем»)** - перспективные технологии, по которым делаются прототипы/исследования, но пока нет серьёзной зависимости бизнеса.
- **Hold («ограничиваем/выводим»)** - технологии, которые не рекомендуется использовать в новых инициативах; по ним планируется миграция или вывод.

Точка на радаре - это конкретная технология/подход в одном из квадрантов с указанием кольца и поддерживаемых бизнес-сценариев.


## 2. Технологии по квадрантам и кольцам

Ниже перечислены ключевые технологии Future 2.0. Для каждой указаны:
- квадрант и кольцо;
- краткая роль в архитектуре;
- бизнес-сценарии (S1–S5), на которые она влияет.


### 2.1. Платформы и операции

#### 2.1.1. Облачная платформа (IaaS/PaaS)

- **Квадрант:** Платформы и операции  
- **Кольцо:** Trial  
- **Сценарии:** S1, S2, S3, S4  
- **Роль:** базовая инфраструктура для развёртывания Платформы данных, доменных сервисов и портала самообслуживания. Даёт эластичность и отказоустойчивость по сравнению с on‑prem, снижает риски по P4/P8 и помогает масштабироваться под новые домены и партнёров.


#### 2.1.2. Data Lakehouse (объектное хранилище + движки обработки)

- **Квадрант:** Платформы и операции  
- **Кольцо:** Trial  
- **Сценарии:** S1, S2, S3, S4  
- **Роль:** целевая платформа хранения и обработки аналитических данных Future 2.0. Позволяет разгрузить Legacy DWH, строить доменные витрины (DomainMarts) и ускорить отчётность, а также дать устойчивые наборы данных для финтех- и ИИ-команд.


#### 2.1.3. Legacy DWH (SQL Server 2008)

- **Квадрант:** Платформы и операции  
- **Кольцо:** Hold  
- **Сценарии:** S1, S2, S3, S4 (как источник истории)  
- **Роль:** текущий источник исторических данных и существующей отчётности. Является корнем проблем P1/P2/P3, поэтому новая логика не добавляется в DWH, он используется только как источник для Платформы данных до завершения миграции.


#### 2.1.4. Стриминговая платформа (Kafka или аналог)

- **Квадрант:** Платформы и операции  
- **Кольцо:** Trial  
- **Сценарии:** S1, S2, S3, S4  
- **Роль:** основа событийной архитектуры для будущих потоков: транзакции финтеха, телеметрия оборудования, события клиник и ИИ. Обеспечивает near real‑time данные для аналитики и ИИ‑сервисов, не нагружая DWH.


#### 2.1.5. Интеграционная шина (ESB, Apache Camel)

- **Квадрант:** Платформы и операции  
- **Кольцо:** Hold  
- **Сценарии:** S1–S4 (на время миграции)  
- **Роль:** существующий канал интеграций между системами. Ограничивает масштабируемость и гибкость, поэтому новые интеграции по возможности строятся через стриминговую платформу и DataAPI, а шина постепенно выводится из ключевых контуров.


#### 2.1.6. Операционные ядра доменов (ClinicCore, FintechCore, AIServices)

- **Квадрант:** Платформы и операции  
- **Кольцо:** Adopt  
- **Сценарии:** S1–S4, косвенно S5  
- **Роль:** операционные системы основных доменов (клиники, финтех, ИИ). Для техрадара важно, что они становятся основными «поставщиками» событий и данных в Платформу данных через Ingestion/Streaming, а не через жёсткую связку с DWH.


### 2.2. Инструменты

#### 2.2.1. Портал самообслуживания / BI (Self-Service Portal)

- **Квадрант:** Инструменты  
- **Кольцо:** Asset -> Trial  
- **Сценарии:** S1, S2, S4  
- **Роль:** целевой интерфейс для бизнес‑пользователей доменов. Позволяет строить отчёты и витрины поверх доменных данных без участия команды DWH. Является ключевой частью решения проблем P1 и P5 и основным результатом по итогам года.


#### 2.2.2. Каталог данных и lineage (Data Catalog)

- **Квадрант:** Инструменты  
- **Кольцо:** Trial  
- **Сценарии:** S1–S5  
- **Роль:** реестр наборов данных, доменных витрин и их владельцев с прослеживаемостью (lineage). Основа для self‑service аналитики, аудита использования данных и внедрения федеративного управления (домен «Безопасность и управление данными»).


#### 2.2.3. Сервис управления доступом и политиками (Security Service)

- **Квадрант:** Инструменты  
- **Кольцо:** Trial  
- **Сценарии:** S5, косвенно S1–S4  
- **Роль:** централизованная реализация RBAC/ABAC, маскирования, анонимизации и аудита доступа к медицинским и финансовым данным. Позволяет реализовать единые политики при сохранении доменной автономии и снизить риски регуляторных нарушений.


#### 2.2.4. Инструменты загрузки данных (CDC/ETL/Ingestion)

- **Квадрант:** Инструменты  
- **Кольцо:** Trial  
- **Сценарии:** S1–S4  
- **Роль:** набор инструментов для batch/stream загрузки из Legacy DWH, операционных систем и партнёров в Data Lakehouse и стриминговую платформу. Обеспечивает постепенную миграцию нагрузки с DWH на новую Платформу данных.


#### 2.2.5. DataAPI (REST/GraphQL) и API Gateway для доступа к данным

- **Квадрант:** Инструменты  
- **Кольцо:** Trial  
- **Сценарии:** S2, S3, S4  
- **Роль:** единый способ доступа доменов и партнёров к агрегированным и обезличенным данным Платформы. Позволяет развивать финтех‑ и ИИ‑сервисы независимо от DWH и упрощает подключение новых бизнесов.


#### 2.2.6. Мониторинг и observability‑стек

- **Квадрант:** Инструменты  
- **Кольцо:** Adopt  
- **Сценарии:** S1–S4, косвенно S5  
- **Роль:** мониторинг пайплайнов данных, задержек, качества и доступности портала самообслуживания и доменных витрин. Критичен для поддержания качества медицинских и финансовых сервисов на фоне роста нагрузки.


#### 2.2.7. Легаси‑BI поверх DWH

- **Квадрант:** Инструменты  
- **Кольцо:** Hold  
- **Сценарии:** S1 (пока)  
- **Роль:** текущий слой отчётности, тесно завязанный на Legacy DWH. Используется до перевода основных отчётов в новый портал self‑service и затем поэтапно выводится.


### 2.3. Практики и паттерны

#### 2.3.1. Data Lakehouse как архитектура данных

- **Квадрант:** Практики и паттерны  
- **Кольцо:** Trial  
- **Сценарии:** S1, S2, S3, S4  
- **Роль:** целевой подход к организации аналитического слоя: слои сырых данных, очищенные доменные зоны и витрины. Позволяет создать единую Платформу данных для клиники, финтеха, ИИ и партнёров.


#### 2.3.2. Data Mesh и доменные data products

- **Квадрант:** Практики и паттерны  
- **Кольцо:** Asset -> Trial  
- **Сценарии:** S2, S3, S4, S5  
- **Роль:** организационный и архитектурный подход, при котором домены (Клиника, Финтех, ИИ, Партнёры, Внутренние операции) владеют своими продуктами данных (data products) и отвечают за их качество. Платформа данных обеспечивает общие стандарты и инструменты, не блокируя развитие доменов.


#### 2.3.3. Федеративное управление данными (Federated Data Governance)

- **Квадрант:** Практики и паттерны  
- **Кольцо:** Adopt  
- **Сценарии:** S5, косвенно S1–S4  
- **Роль:** модель управления, при которой единые правила по качеству, безопасности и метаданным задаются доменом «Безопасность и управление данными», а исполнение и подробная ответственность распределены между доменами.


#### 2.3.4. DataOps и MLOps

- **Квадрант:** Практики и паттерны  
- **Кольцо:** Asset  
- **Сценарии:** S1, S3, S4  
- **Роль:** практики автоматизации жизненного цикла data‑пайплайнов и ML‑моделей (контроль версий, тестирование, развёртывание, мониторинг). Важны для устойчивости ИИ‑сервисов и качества отчётности на фоне частых изменений данных.


#### 2.3.5. Infrastructure as Code (Terraform и аналоги)

- **Квадрант:** Практики и паттерны  
- **Кольцо:** Trial  
- **Сценарии:** S1–S4, S5  
- **Роль:** описывание инфраструктуры (облако, кластеры, сервисы Платформы данных) в виде кода. Повышает воспроизводимость, снижает риск ошибок при развёртывании и упрощает аудит инфраструктурных изменений.


### 2.4. Языки и фреймворки

#### 2.4.1. Python и ML/data‑стек

- **Квадрант:** Языки и фреймворки  
- **Кольцо:** Adopt  
- **Сценарии:** S1, S3, S4  
- **Роль:** основной язык для data‑инженеров и команд ИИ/ML. Используется для построения пайплайнов обработки данных, обучения моделей, сервисов аналитики и интеграции с Платформой данных.


#### 2.4.2. Go/Java для сервисов (FintechCore, AIServices и др.)

- **Квадрант:** Языки и фреймворки  
- **Кольцо:** Adopt  
- **Сценарии:** S2, S3, S4, S5  
- **Роль:** основные языки для высоконагруженных и критичных по SLA сервисов (финтех, ИИ, интеграция). Позволяют масштабировать сервисы и выполнять регуляторные требования по надёжности и производительности.


#### 2.4.3. SQL / аналитический SQL

- **Квадрант:** Языки и фреймворки  
- **Кольцо:** Adopt  
- **Сценарии:** S1–S4  
- **Роль:** основной язык запросов к витринам, Lakehouse и DWH. Остаётся ключевым инструментом для аналитиков и отчётности, но в целевой архитектуре используется поверх доменных витрин, а не напрямую к монолиту DWH.


#### 2.4.4. PowerBuilder (клиентский интерфейс операторов)

- **Квадрант:** Языки и фреймворки  
- **Кольцо:** Hold  
- **Сценарии:** S1 (как источник операционных данных)  
- **Роль:** текущий клиентский интерфейс операторов в клиниках. Новые интерфейсы строятся на веб‑технологиях, PowerBuilder постепенно выводится по мере модернизации операционных систем, однако до завершения миграции остаётся частью ландшафта.
