# Обоснование конфигурации Terraform для Future 2.0

## 1. Цель и контекст

Цель конфигурации - получить минимальную, но реалистичную IaaS‑инфраструктуру в Yandex Cloud,
которая поддерживает целевую архитектуру Future 2.0: на выделённой виртуальной машине
разворачивается стек Платформы данных (Lakehouse/Data Mesh, Airflow, каталог данных и т. д.),
а управление базовыми ресурсами выполняется через Terraform как IaC‑инструмент.

Настоящая конфигурация автоматизирует создание IaaS‑контуров
(сеть + VM + диск) под среду разработки/тестирования Future 2.0.

## 2. Выбор ресурсов и параметров

### 2.1. Модель облака и провайдер

Используется публичное облако Yandex Cloud по модели IaaS:

- даёт управляемые ресурсы (вычисление, сеть, диски) без забот о «железе»;
- поддерживает Terraform‑провайдер, что позволяет описывать инфраструктуру декларативно;
- расположен в подходящем регионе и позволяет гибко масштабировать ресурсы по мере роста Future 2.0.

### 2.2. Сеть (VPC и подсеть)

Ресурсы:

- `yandex_vpc_network.this` - отдельная VPC‑сеть `future2-vpc`;
- `yandex_vpc_subnet.public` - подсеть `future2-public-subnet` в зоне `ru-central1-a`
  с диапазоном `10.10.0.0/24`.

Обоснование:

- Выделенная VPC создаёт изолированный контур для Future 2.0, не смешивая трафик с другими
  проектами в облаке.
- Подсеть с собственным адресным пространством упрощает будущую декомпозицию:
  можно будет добавить отдельные подсети под разные домены (Клиника, Финтех, ИИ)
  или под окружения (dev/test/prod).
- Сеть создаётся Terraform - это позволяет в дальнейшем версионировать изменения
  в топологии и поднимать идентичные контуры для разных окружений.

### 2.3. Виртуальная машина

Ресурсы:

- `yandex_compute_instance.platform` - VM `future2-data-platform-dev`;
- образ ОС определяется через `data "yandex_compute_image" "ubuntu"` (семейство `ubuntu-2204-lts`);
- конфигурация: `vm_cores = 4`, `vm_memory = 8` (ГБ).

Обоснование параметров:

- Ubuntu 22.04 LTS - распространённый и поддерживаемый дистрибутив, который хорошо подходит
  для запуска Docker, Airflow, Dremio, MinIO и других компонент.
- 4 vCPU и 8 ГБ RAM - разумный минимум, чтобы одновременно держать несколько контейнеров
  (Lakehouse, каталог, оркестратор) и при этом иметь запас для экспериментов с пайплайнами.
- Имя VM и другие параметры вынесены в переменные, что позволяет легко переиспользовать модуль
  для отдельных окружений: `future2-data-platform-dev`, `future2-data-platform-test` и т. д.

### 2.4. Диск

Ресурс:

- `yandex_compute_disk.platform` - диск типа `network-ssd` с размером `vm_disk_size_gb` (по умолчанию 50 ГБ),
  привязанный как `boot_disk` к VM.

Обоснование:

- Network SSD даёт более предсказуемую производительность ввода‑вывода по сравнению с HDD
  и подходит для хранения образов контейнеров, временных данных и логов Платформы.
- 50 ГБ достаточно для:
  - базовой ОС;
  - docker‑образов (MinIO, Nessie, Dremio, Airflow, Postgres и др.);
  - тестовых наборов данных и логов.
- Размер вынесен в переменную (`vm_disk_size_gb`), чтобы при переходе от dev к prod можно было
  легко увеличить объём без изменения структуры конфигурации.

### 2.5. NAT и доступ снаружи

В блоке `network_interface` виртуальной машины включён `nat = true`:

- для VM автоматически выделяется внешний IP‑адрес;
- сохраняется отдельный внутренний адрес в подсети `10.10.0.0/24`.

Обоснование:

- Для dev-окружения и первых MVP такой подход проще всего:
  - можно подключаться по SSH напрямую;
  - можно открывать веб‑интерфейсы MinIO, Dremio, Airflow etc. через внешний IP.
- В дальнейшем, при усилении требований безопасности, можно будет заменить прямой доступ через NAT
  на bastion‑хост, VPN или балансировщик - конфигурация Terraform это позволяет.

### 2.6. Что разворачивается вручную

Terraform управляет только IaaS‑уровнем:

- сеть (VPC + подсеть),
- диск,
- виртуальная машина и её метаданные (SSH‑ключ).

Ручные (или отдельным инструментом) шаги:

- генерация SSH‑ключа (`ssh-keygen`) на рабочей станции и его регистрация в `metadata`;
- установка Docker/Docker Compose на VM;
- запуск стека Платформы данных по docker-compose (MinIO, Nessie, Dremio, Airflow, DataHub и т. д.).

Такое разделение подчёркивает границу ответственности: Terraform управляет инфраструктурой,
а прикладной стек может разворачиваться другими средствами (скрипты, Ansible, Helm и т. п.).

## 3. Почему декларативный подход и Terraform

Конфигурация описана декларативно:

- мы задаём желаемое состояние: «есть сеть, подсеть, диск и VM с такими параметрами»;
- Terraform сам:
  - вычисляет зависимости между ресурсами (сначала сеть, затем подсеть, затем диск и VM);
  - хранит фактическое состояние в `terraform.tfstate`;
  - сравнивает текущее состояние с конфигурацией и определяет, что нужно создать, изменить или удалить.

Преимущества по сравнению с ручной настройкой:

- **Предсказуемость**. Перед изменениями всегда есть `terraform plan`, который показывает,
  какие ресурсы будут добавлены/изменены/удалены.
- **Идемпотентность**. Повторный запуск `terraform apply` не создаёт «лишних» машин/сетей -
  Terraform приводит инфраструктуру к описанному состоянию, а не «просто выполняет команды».
- **Поддерживаемость**. Конфигурация хранится в git‑репозитории, по ней видно историю изменений
  и можно делать code‑review так же, как по обычному коду.

## 4. Воспроизводимость и масштабируемость с помощью IaC

Воспроизводимость:

- Чтобы поднять ещё одно окружение Future 2.0, достаточно:
  - склонировать репозиторий;
  - скорректировать `terraform.tfvars` (ID каталога, имена, размеры);
  - выполнить `terraform init && terraform apply`.
- Один и тот же код можно использовать в разных папках/облаках/зонах, меняя только значения переменных.

Масштабируемость:

- При росте нагрузки можно:
  - увеличить параметры VM (`vm_cores`, `vm_memory`, `vm_disk_size_gb`);
  - добавить ещё несколько VM с тем же модулем (например, для отдельных доменов);
  - расширить сеть (новые подсети под финтех, ИИ, партнёров).
- Все изменения описываются в коде, а не «вручную» через консоль провайдера, что:
  - уменьшает риск ошибок;
  - позволяет откатываться к предыдущим версиям конфигурации;
  - даёт прозрачность для команды и ревью.

## 5. Связь с бизнес-целями Future 2.0

Эта конфигурация поддерживает ключевые сценарии S1–S4 из предыдущих заданий:

- **S1 - быстрая подготовка отчётности**: инфраструктура для Платформы данных и Lakehouse
  разворачивается за минуты, а не недели, что сокращает time‑to‑market для новых отчётных витрин.
- **S2 - независимое развитие финтеха** и **S3 - ИИ‑направления**:
  можно создать отдельные окружения для команд финтеха и ИИ, не затрагивая Legacy DWH
  и не конкурируя за ресурсы в монолитной инфраструктуре.
- **S4 - масштабирование на новых партнёров**:
  при появлении новых доменов/партнёров инфраструктура расширяется кодом (новые подсети, VM, стеки),
  а не ручной настройкой.

В сумме выбранная конфигурация демонстрирует практическое применение IaC и Terraform:
инфраструктура Future 2.0 становится таким же артефактом в репозитории, как код сервисов
и пайплайнов данных, что напрямую снижает операционные риски и ускоряет развитие платформы.
